# NMA：Agent 间结构化通信 + 同行审查协议

> v1.0
> **一句话**：Agent 之间的协作消息必须结构化、可追溯、可验证；审查把"我觉得没问题"变成"命令 Y 证明 X"。
> **定位**：NMA = **Part A 通信层**（派发/回报/查询/交接——日常协作的骨架）+ **Part B 审查层**（验收/同行审查/多 critic）。两层共用同一套消息与引用纪律：所有协作都落在结构化消息和可解析引用上，不靠自由文本。

## Part A — Agent 间结构化通信

### 1. 为什么不用自由文本

自由文本协作的五个问题（原始设计问题定义）：

1. **信息密度低**：来回多轮才能覆盖全部决策点
2. **遗漏风险高**：没有强制覆盖清单，关键项可能没人问
3. **术语不一致**：同一个词在两边含义不同
4. **不可追溯**：谁问了什么、谁答了什么，散落在聊天记录里
5. **无法复用**：下一个 Agent 想了解背景，必须翻整个聊天历史

结构化通信的目标：**每条协作消息是一个有类型、有必填字段、有引用、可重放的事件**，而不是一段散文。

### 2. 消息模型

（数据模型对齐 A2A 1.0 的 Task/Message/Part/Artifact 分层：任务有状态机，消息是回合，内容分片，产出是 artifact。）

**必填字段**：

| 字段 | 说明 |
|------|------|
| `message_id` | 全局唯一；幂等键（重复投递按它去重） |
| `task_id` | 所属任务；跨任务消息必须新建任务引用 |
| `project_id` | 可选（单任务场景省略） |
| `from` / `to` | 执行体身份（roster 中的角色/成员 ID） |
| `type` | 封闭清单见 §3 |
| `refs[]` | 内容引用：CAP-STORE artifact ref（含指纹）/ CAP-STATE 事件 ref / 文件路径 |
| `status` | 消息状态：`submitted` / `working` / `input-required` / `completed` / `failed` / `cancelled` |
| `created_at` | 时间戳（审计与排序用） |

**可选字段**：`correlation_id`（回复哪条消息）、`deadline`（应答期限）、`deadline_fallback`（超时兜底动作）、`summary`（一句话摘要；**摘要不是证据**）。

**内容形态**：`text`（摘要/说明，可省略）/ `file_ref`（artifact 引用）/ `data`（结构化字段）。**验收、审查、闭环只能引用 `refs[]` 指向的 artifact，不得引用消息正文。**

### 3. 消息类型（封闭清单）

| type | 用途 | 方向 | 必填额外字段 |
|------|------|------|--------------|
| `DELEGATE` | 派发任务 | 编排者 → 执行者 | `goal` / `acceptance[]`（结构化验收标准）/ `delivery`（交付位置）——三要素；缺一 = 派发无效，接收方有权退回 |
| `ACK` | 认领/退回 | 执行者 → 编排者 | `accepted`（true/false）+ 退回理由 |
| `PROGRESS` | 进展（可选） | 执行者 → 编排者 | `current_step`（不产生验收语义） |
| `COMPLETE` | 完成 | 执行者 → 编排者 | `artifact_refs[]` + `summary` + `evidence[]`；落 `SIG-COMPLETE` |
| `QUERY` | 提问（可阻塞） | 任意 → 任意 | `question` + `blocking`（true/false） |
| `DECISION_REQUEST` | 需人类决策 | 任意 → 人类（经 CAP-ATTN） | `options[]` + `recommendation` + `impact` + `deadline`（见 04-NMH §8） |
| `HANDOFF` | 跨团队交接 | 编排者 → 编排者 | `brief_ref` + `decision_refs[]` + `constraints[]`（见 07-HANDOFF） |
| `ESCALATE` | 升级 | 任意 → 上级 | `reason` + `positions[]` + `evidence[]`（见 09-GOVERNANCE） |

新增类型必须走协议版本变更（minor）；类型不可由执行体自定义。

### 4. 通信纪律

1. **引用不内联**：内容给 `refs`，不把长文塞进消息正文（上下文隔离；正文摘要不得作为验收依据）。
2. **落状态**：每条消息写入 CAP-STATE（事件日志），可按 `message_id` / `task_id` 重放。
3. **幂等**：`message_id` 重复投递只生效一次；重试沿用同一 `message_id`。
4. **ACK 必回**：`DELEGATE` 必须在 `deadline` 内收到 `ACK`；超时 = 异常，走 `ESCALATE` 或重派，不静默等待。
5. **状态从状态读**：任务状态以 CAP-STATE 为准；不靠聊天记忆、不靠"我记得我发过了"。
6. **通知面**：消息投递走 CAP-NOTIFY 代码级事件（V5 可订阅）；IM 文本只是派生视图（V4/V6 语义适用）。
7. **终态不可续**：`completed` / `failed` / `cancelled` 的任务不再接受新消息（对齐 A2A 终态语义）；继续协作 = 新任务。

### 5. 与审查的关系

- 审查（Part B）消费 Part A 的 `refs[]` 与 `evidence[]`，不消费正文叙事。
- 审查结论本身以消息回传：`type=COMPLETE` 的验收结果落 `SIG-VERDICT`；驳回 = `QUERY` 或 `ESCALATE`，附理由与证据。
- 通信层不做质量判断；审查层不定义消息格式。两层解耦，靠引用相连。

## Part B — 审查

### 6. 审核定位与触发

**NMA 的审查层是审查协议**：验证"声称完成"是否真实。

**触发场景**（满足任一）：
- Worker 提交交付件，属于**需审核类别**（代码/配置/方案/文档——哪些类别由绑定层角色实例表定义）
- 任何 Agent 显式请求审核
- 项目验收前的终审（leader 对最终产出的验收）

**审核方 ≠ 被审核方**（利益分离；谁审谁 = 绑定层角色实例表）。

### 7. 双模式

| 模式 | 适用 | 核心机制 |
|------|------|---------|
| **Checklist 验票** | 代码 / 配置 / 可验证产出 | 三要素 scorecard（§8）——每项一个可执行命令，结果可复现 |
| **同行审查** | 文档 / 方案 / 设计 | 结构化质疑（§9）——逐条意见 + 回应 + 锁定 |

判断标准：**产出能否用命令验证？** 能 → Checklist；不能 → 同行审查；混合产出各走各的。

### 8. Checklist 验票（scorecard 三要素）

| 要素 | 要求 |
|------|------|
| 具体命令 | 可复制执行的 shell/grep/curl/API 调用 |
| 预期结果 | 明确的通过标准（不是"看起来对"） |
| 执行者标记 | 🟢 = 被审核方执行 / 🔵 = 审核方验证 / ❌ = 不可执行（注明原因） |

```
审核方发 Checklist（@被审核方）
  每条: [C{n}] {检查什么} — 命令: {cmd} — 预期: {result} — 状态: 🔓
被审核方逐条执行 🟢 项 → 贴命令输出 → ✅（附输出证据）
审核方独立验证 🔵 项（只能做自己能访问的外部检查——
  跨 workspace 的文件检查做不到就标 ❌，不假装）
全部 ✅ → 通过；任一 ❌ 有实质问题 → ⚠️ 驳回（附理由）
```

**来源抽查（与 04-NMH §7 配套）**：审核方随机抽取 N 个含事实断言的节点/条目，要求给出可解析来源（文件+行 / CAP-STORE ref+指纹 / 外部文档 / 人类原话）；给不出来源 → 该条直接 ⚠️。**不询问模型"你确定吗"，只检查来源是否存在且可复现。**

**隔离边界**：审核方不能进被审核方的 workspace 执行命令。🔵 项限于 API 端点、对象存储可读文件、公开文档等外部可验证面。

### 9. 同行审查（文档/方案）

```
审核方读产出 → 发结构化审查（@被审核方）
  [R{n}] {位置/章节} — {问题或质疑} — 严重度: 阻断/建议/提问 — 状态: 🔓
被审核方逐条回应（接受改 / 不接受说明理由 / 请求澄清）
  状态: ✅（双方同意）/ ⚠️（驳回待改）/ 🏳️（僵持）
全部 ✅ → 通过；有 ⚠️ → 改后复审；有 🏳️ → 升级
```

**审查解释要求（学习闭环）**：每个锁定/驳回必须附一句话理由——"为什么通过/被驳回"。无理由的审核 = 黑箱，协议违规。

### 10. 人类同行优先

存在匹配领域的人类同行且在场 → **先给人审**。Agent 审核是替代不是补充——human 可用时，human 判断是最终参考（Agent 可补充技术验证，不覆盖 human 判断）。
默认实践：各 human 领域不同时，NMA 默认走 Agent 审核，human 抽查 + 仲裁（🏳️ 时介入）。

### 11. 🏳️ 升级路径（模式依赖）

| mode | 升级对象 |
|------|---------|
| single_user | arbitrator 仲裁 |
| multi_user | leader（团队内）；方向性僵持 → 建议当事人 human 直接沟通 |

升级内容 = 双方立场（各一段）+ 分歧点 + 各自依据。**不升级情绪，只升级事实和分歧。**

### 12. 多 Critic 投票（MC-1~10，扩展 B-6）

**实证前提**：9 个前沿 LLM（7 模型族）面板有效独立票 ≈2——同构 critic 的多数投票统计上等价于单 critic 加噪声（面板准确率比独立投票低 8-22pp）。**因此不全量引入：条件启用 + 异构约束。**

**启用条件（必须同时满足）**：
- **MC-1** 该交付是人锁关键交付：`critical_delivery: true`（accountable stakeholder 在 loop_spec/task spec 显式声明；不由执行体自判"这很重要"）
- **MC-2** 验收结论具有不可逆或高外部影响（R1 类）
- **MC-3** critic 池满足异构约束（MC-4）；不满足 → 降级为**单 critic + 强制 dissent 记录**（不得声称"多 critic 投票"）

**异构约束**：
- **MC-4** N 个 critic 必须来自 ≥2 个不同模型族（或可证明不同训练分布的执行体）；同族多实例不增加独立票数。绑定必须声明 critic 池模型族组成；无法声明或不满足 → 不得启用
- **MC-5** N 个 critic = N 个独立 fresh 子代理（CAP-SPAWN X1），context_refs 相同（spec + artifact ref + signal ref），不得共享中间结论、不得互相可见评分
- **MC-6** 每个 critic 独立记录 verdict 和理由；理由必须含 ≥1 条"如果不同则可能出错的假设"（dissent 显式化），不得只给分数

**投票规则**：
- **MC-7** 严格多数（>N/2）通过/不通过
- **MC-8** 平票（N 偶数各半）→ **不重投**，直接升级 accountable（重投 = 相关错误被重复计数）
- **MC-9** 每个 critic 的 verdict/理由/dissent 写入决策记录；**即使多数通过，少数意见必须保留**（下次 re-plan 的输入）
- **MC-10** 不改变 B-6 死环边界：同一 criterion 的"打回"按**投票轮**计不按单个 critic 计（第 1 轮 2 票不通过 1 票通过 = 1 次 mismatch）；第 3 轮分歧（无论几个 critic）→ 冻结升级 human；一致轮不消耗 mismatch 预算

**成本集成**：N critic = N spawn 全计入 spawn 预算。超预算降级 ≠ 纯单 critic（破坏可靠性语义）→ **"单 critic + 强制 dissent + 人锁验收"**（人必须显式确认单 critic 结论）。

### 13. B-6：critic 死环防护

verification mismatch（critic 打回但 spec 无歧义可改）的死循环边界：

1. mismatch 进入**规格澄清通道**：24h accountable 裁决窗口（CAP-TIMER 承载）
2. 窗口超时 = **维持原 spec** + critic 记 dissent 且**必须仍出评分卡**（不得空手）
3. 同一 criterion 最多 2 轮打回，**第 3 轮冻结**（升级 human）
4. **终裁权 = human；critic 是质量信号，非否决权**

计数与窗口判定 = 确定性脚本（`core/scripts/verification-mismatch-window.sh`），不是 LLM 自觉。

### 14. 禁止 / 必须

- ❌ 用自由文本代替结构化消息派发任务（三要素必须作为 `DELEGATE` 字段）
- ❌ 把消息正文/摘要当验收证据（只认 `refs[]`）
- ❌ 假验证（没跑命令就标 ✅）
- ❌ 静默驳回（驳回必须 @被审核方 + 理由）
- ❌ 审核方越界改被审核方的产出（提意见可以，动手 = 角色混淆）
- ❌ 无理由的锁定
- ❌ critic 用"重要"自启多 critic（MC-1 人锁）
- ✅ Checklist 输出证据必须贴原文（截断可，伪造不可）
- ✅ 验收判定只能引用已标记 signal + artifact ref（§11-SIGNAL 效应 2）
